# 真实模型 Token 消耗验收

验收日期：2026-10-20（Asia/Shanghai）。模型：现有配置的 `deepseek-flash`。

**结论：生成阶段观察到改善，但端到端的 Token 优化验收未通过。** 两项功能同时开启时，研究和生成消耗从基线的 156,183 降到 105,327 Token，减少 **32.56%**；但该组最终摘要复核失败，不能把它计为成功交付的节省。仅开启上下文整理的那次运行虽然完成任务，总 Token 却增加 **12.28%**。

这是三组自由运行各一次的真实 API 实测，不是前一报告的 HTTP 模拟或字符数估算。三组没有重跑后挑选较低结果；失败组的消耗全部保留。没有修改生产筛选规则、复核规则或 `.env` 来使本次结果通过。

## 测量条件

- 来源池为前次真实验收留下的 42 条新闻：40 条 arXiv 公告、2 条 TechCrunch 条目。取自 [原始验收记录](live-acceptance-20261019T130235Z.json) 的服务器材料归档；本次不重新联网抓新闻。
- 三组可用的来源条目、正文缓存、用户身份、关注词、排除词和 5 条历史简报条目相同。历史使用前次已生成的 5 条简报内容，构成重复订阅场景。
- 任务时钟固定在 `2026-10-19T13:03:36.098040+00:00`，因此回放时不会把旧快照按今天的时间窗口判为过期。本报告不声称这些是 10 月 20 日的实时新闻。
- 使用同一模型和生产 `run_live` / `create_agent` 入口，工具调用顺序、次数、选稿、补读和结束仍由真实模型决定。没有固定模型响应或强制工具计划。
- 最终摘要复核三组均开启，每条规则、正文上限相同；每组最多 24 次工具调用，验收超时统一为 300 秒，单模型请求超时 90 秒，SDK 自动重试关闭。没有外部推送。
- 冻结快照保存了 6 篇已核实原文。缓存没有的页面不重新抓取，`read_article` 如实返回 RSS 回退提示。三组最终均使用了 1 篇缓存原文，另有 RSS 回退；这能控制输入，但不能替代重新联网的来源质量验收。

**自由选源带来一个限制**：来源池一致，但基线实际只获取了 40 条 arXiv；另两组还获取了 2 条 TechCrunch。后者开启预筛选后去掉 5 条历史，剩 37 条候选。最终选稿也并不完全相同。因此这是同条件下的业务运行观察，不能将百分比全部归因于某一条确定性规则，也不是统计显著的平均收益。

## 实际用量

以下全部来自提供商 HTTP 响应的原始 `usage`。输入 Token 包含缓存命中；输出 Token 已包含推理输出，推理数量只作分项，不再次加到总数。[DeepSeek API 用量字段说明](https://api-docs.deepseek.com/api/create-chat-completion/)。

| 组别 | 预筛选 | 上下文整理 | 生成阶段 Token | 最终复核 Token | 已消耗总 Token | 最终结果 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| `baseline` | 关 | 关 | 156,183 | 9,905 | 166,088 | 完成，5 条，复核通过 |
| `context_only` | 关 | 开 | 174,507 | 11,977 | 186,484 | 完成，5 条，复核通过 |
| `prefilter_and_context` | 开 | 开 | 105,327 | 24,536 | 129,863 | 生成 5 条草稿，复核失败 |

解释：

- 两项都开，**生成阶段**相对全部关闭少 32.56%，相对仅上下文整理少 39.64%。研究阶段没有出现工具错误，37 条候选中 32 条由模型排除、5 条入选。
- 仅上下文整理，生成阶段比基线多 11.73%，含复核的总消耗多 12.28%。这次运行出现一次未知文章 ID 的批量状态提交错误，后续修正，并在提交后继续补读；不能从累计上下文变短直接推断整个 Agent 更省 Token。
- 联合组的 **129,863 是一次失败任务已消耗的 Token**，不能据此宣称成功简报的总成本下降。比较脚本只对成功且完整计量的端到端配对给出节省百分比，该组端到端百分比保留为 `null`。
- 三组共 30 次真实模型请求，均返回 usage，无漏计请求；本次总消耗 **482,435 Token**，包含失败复核和一次修正请求，不把失败成本隐藏在成功样本之外。

| 组别 | 生成请求 | 复核请求 | 工具调用 | 耗时（秒） |
| --- | ---: | ---: | ---: | ---: |
| baseline | 8 | 1 | 15 | 70.17 |
| context_only | 10 | 1 | 18 | 108.50 |

## 缓存与推理消耗

即便生成阶段的总 Token 下降，也不能由此断言费用下降。本次没有按价格计算账单。

| 组别 | 全阶段输入 Token | 缓存命中 Token | 未缓存输入 Token | 输入缓存命中率 | 输出 Token（含推理） | 其中推理 Token |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| baseline | 152,105 | 121,984 | 30,121 | 80.20% | 13,983 | 9,071 |
| context_only | 164,582 | 66,432 | 98,150 | 40.36% | 21,902 | 12,834 |
| prefilter_and_context | 101,302 | 43,776 | 57,526 | 43.21% | 28,561 | 20,419 |

已观察到：启用上下文整理的两组缓存命中率较低，联合组的未缓存输入仍高于基线。可能原因是工作清单放在消息前部且随状态重建，改变了较长的请求前缀；这是结合请求归档和前缀缓存机制的推断，不是独立的缓存实验。顺序执行带来的缓存冷热差异也未消除。[DeepSeek 缓存机制说明](https://api-docs.deepseek.com/guides/kv_cache/)。

## 业务与失败检查

通过的检查：

1. 所有真实获取的来源条目逐字段等于冻结输入，没有串用变化后的 RSS。
2. 联合组恰好保留预期的 37 个候选，过滤原因全为 `history_id`，数量 5；没有额外误删文章。五个历史 ID 在其所有实际工作清单中均不存在。
3. 上下文整理两组，每轮至多一份工作清单，模型排除项不携带长文或证据全文。
4. 三组草稿都没有重复历史条目。两组成功简报各 5 条，条数上限、已取得材料校验及最终引用、数值复核通过。
5. 每次 usage 均满足 `prompt_tokens + completion_tokens = total_tokens`，且缓存命中加未命中等于输入 Token。

未通过的检查：

联合组在最终复核阶段连续两次未通过输出结构校验。第一次返回的 JSON 语法有效，但顶层使用 `articles`，程序要求的是 `items`。离线重新校验第一份响应，确认错误为 `items` 缺失、`articles` 为多余字段。第二次修正仍未通过，按既有规则任务失败，未放宽校验或发布草稿。

生产错误提示将这类结构问题概括为“未返回有效 JSON”，未向修正请求指出具体字段差异；这是本次暴露的可改进点。第二次响应没有保存正文，只有 usage、结束原因和最终校验错误，因此不推断它与第一次完全相同。

```powershell
uv run --locked python -m scripts.benchmark_tokens --output docs/token-benchmark-new.json
```

该脚本继续使用同一份已捕获的真实新闻，不会刷新当天来源。新文件名用于保留本次原始记录；已记录的失败组不会被 `--resume` 自动重跑或替换。

本次新增三项不付费的计量和输入保护测试，全量结果：**89 passed in 14.42s**；Ruff 检查通过。测试覆盖缓存与推理不重复计数、失败或漏计样本不计算节省，以及快照不被工具修改。

后续优先级：先改善复核的字段校验反馈和成功提交后的结束约束；再评估工作清单的位置及缓存前缀稳定性；之后用固定来源覆盖、多个独立重复样本重新比较成功交付的总 Token。当前证据不足以宣称端到端优化已验收通过。
