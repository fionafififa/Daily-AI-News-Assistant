## 验收结论

最终版本三种场景均完成：工程师首次订阅 5 条、同用户历史去重 5 条、研究者首次订阅 3 条。全部已站内推送，工程师第二份与第一份没有重复文章 ID。52 项自动化测试、Ruff 检查与格式检查、JavaScript 语法检查通过。桌面和手机的 9 项浏览器检查通过，无脚本错误、无横向溢出。

两项原有问题已针对性复测：

- **数值语义**：最终 PRIME 摘要为“平均得分从 30.1 提高到 59.2（满分 100）”。另将历史上真实产生的错误摘要连同捕获的原文再次发给真实复核模型，已修复“满分 59.2 / 达到满分”；正确摘要对照保持原样；虚构普遍准确率保证的对照也被纠正。专项 3/3 通过。最终三份简报的 13 条摘要均获 supported；专项回归另行证明了修正能力。
- **时间口径**：13 条入选论文分别保留公告与首次提交日期，检查全部通过。SAI 的 `announced_at=2026-10-19T04:00:00+00:00`，`first_published_at=2026-07-27T03:38:01+00:00`；前端分别显示 RSS 公告和首次提交，未再把公告日称为首次发表日。对于其他无法核实首次提交的内容，显示未知。

复核是同一模型对有界原文的检查，加程序验证，并不保证所有后续摘要都正确。此次是 3 份简报及 3 个专项对照的有限样本。

## 代码修改与原因

原实现把 RSS 的 `published_parsed` 直接放进 `published_at`，下游没有时间类型可区分；现在由 `app/article_time.py` 统一时间语义。`app/sources.py` 把 RSS 时间写入 `feed_entry_at`，arXiv 同时写入 `announced_at`，仅用于 24 小时候选窗口。读取摘要页时解析 `.submission-history` 的 v1 作为 `first_published_at`，后续版本另存 `updated_at`；兼容字段 `published_at` 指向已核实的首次提交日期。页面和邮件分别展示时间标签。只有日期精度的来源保留日期，不臆造时区或精确时刻。

原摘要只依赖生成提示和字段校验，程序无法发现“maximum observed”被译成“满分”。现在 `app/agent.py` 仍运行由模型自主选工具的 `create_agent` 循环，结束后交给 `app/summary_review.py` 做输出复核：

1. 非空简报一次批量请求，只包含最终入选条目的摘要、日期及各篇最多 5000 字符原文；不发送完整工具轨迹或全部 40 条候选。
2. 复核检查数值、分母、比较关系、实验范围及日期，并提供连续原文引用；正确摘要不改写，有依据的错误摘要返回修正文本。
3. 程序验证返回 ID 完整性、JSON 结构、引用是否为原文连续片段，并检查数值来源和“最高实测值/满分”混淆。任何验证失败都不保存为完成、不推送。
4. arXiv `/abs/` 只提取论文摘要，剔除导航，并明确标记“依据论文摘要”。历史输入只携带去重所需字段，避免把复核日志带回后续 Agent 上下文。默认 `SUMMARY_REVIEW_ENABLED=true`；空简报无需新增模型调用。

工具调用顺序仍由 LLM 决定。复核属于推送前的输出校验，不接管研究阶段的工具选择。

## 同一份简报内的 Token 对比

口径：分别累加实际 API usage 中标记为 `generation` 和 `summary_review` 的请求。生成部分视为不增加复核请求时的用量，二者相加为开启复核后的用量；这是同次运行的配对成本分解，不是两组独立 A/B 重跑。计数包含缓存输入及推理输出，全部 24 个成功请求都有 usage。

| 场景 | 条数 | 生成 Token | 新增复核 Token | 增幅 | 复核请求耗时 |
|---|---:|---:|---:|---:|---:|
| 工程师首次订阅 | 5 | 110,680 | 12,264 | +11.08% | 33.41 秒 |
| 工程师历史去重 | 5 | 98,046 | 6,849 | +6.99% | 13.73 秒 |
| 研究者首次订阅 | 3 | 75,653 | 6,005 | +7.94% | 15.64 秒 |
| 合计 | 13 | 284,379 | 25,118 | +8.83% | 62.78 秒 |

开启复核后三份共 **309,497 Token**。本次总 Token 没有成倍增长，额外约 8.83%；但延迟和输出成本的影响较明显：每份多 13.73–33.41 秒，平均 20.93 秒。这里的耗时为复核模型请求实测，并非独立开关 A/B 的端到端时差。

| Token 构成 | 生成 | 新增复核 |
|---|---:|---:|
| 输入 | 270,892 | 8,256 |
| 其中缓存命中 | 203,520 | 384 |
| 未缓存输入 | 67,372 | 7,872 |
| 输出（含推理） | 13,487 | 16,862 |
| 其中推理输出 | 7,052 | 13,493 |

复核的 25,118 Token 中，13,493 来自推理输出，约占 53.7%；额外复核输出 16,862，超过原生成输出 13,487。生成阶段缓存命中较多，复核缓存命中较少。因此 **Token 增幅 8.83% 不代表费用也只增加 8.83%**；此处未按价格估算账单。

日期解析本身是确定性代码，不需要模型请求。与早期 291,987 Token 的旧验收不能直接做因果对比：提示、摘要提取和模型工具选择均有变化，因此用同次运行的分阶段 usage 隔离复核成本。当前 3 份配对比较不包含调试失败和专项对照请求。
